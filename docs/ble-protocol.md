# BLE 통신 규격

park-assist 기기와 안드로이드 앱 사이의 BLE 규격이다.
**이 문서가 규격의 단일 진실 공급원(single source of truth)이다.**
펌웨어와 앱 중 어느 쪽이든 이 문서와 다르게 동작하면 그쪽이 버그다.

규격을 변경할 때는 **이 문서 → 펌웨어 → 앱** 순서로 같은 PR에서 함께 고친다.

## 1. 기기 구성

센서는 **총 8개**이고, 범퍼마다 독립된 ESP32 유닛을 물린다
([ADR 0004](decisions/0004-two-device-split.md)).

| 유닛 | 광고 이름 | 센서 | 채널 |
| --- | --- | --- | --- |
| 후방 | `PARK-01` | 4 | CH1~CH4 |
| 전방 | `PARK-02` | 4 | CH1~CH4 |

**두 유닛은 서비스·캐릭터리스틱 UUID가 완전히 같고 광고 이름만 다르다.**
펌웨어도 동일하며 `ZONE_IS_REAR` 하나만 바꿔 굽는다.

앱은 두 기기에 **동시에** BLE 연결을 유지하고, 각 연결을 독립적으로 재시도한다.
한쪽이 꺼지거나 배터리가 나가도 다른 쪽은 그대로 동작한다.

> ⚠️ 두 유닛이 같은 서비스 UUID를 광고하므로, 서비스 UUID만으로 스캔 필터를 걸면
> 두 연결이 같은 기기를 잡는다. **연결 전에 반드시 광고 이름을 확인해야 한다.**
> 그래서 펌웨어는 광고 패킷(또는 스캔 응답)에 기기 이름을 반드시 실어야 한다.

## 2. GATT 프로파일

| 항목 | 값 |
| --- | --- |
| Service UUID | `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` |
| TX 캐릭터리스틱 (notify, 기기 → 폰) | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` |
| RX 캐릭터리스틱 (write, 폰 → 기기) | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` |
| Battery Service (선택) | `0000180F-0000-1000-8000-00805F9B34FB` |
| Battery Level (선택) | `00002A19-0000-1000-8000-00805F9B34FB` |

Nordic UART Service(NUS)와 같은 UUID 체계를 쓰지만, 스트림이 아니라 **고정 길이
바이너리 패킷**을 주고받는다.

TX/RX 이름은 **기기 관점**이다. 앱은 TX를 구독(notify)하고 RX에 write한다.

### CCCD

TX 캐릭터리스틱의 notify를 켜려면 CCCD 디스크립터
`00002902-0000-1000-8000-00805F9B34FB`에 `ENABLE_NOTIFICATION_VALUE`(`0x01 0x00`)를
write해야 한다. `setCharacteristicNotification()` 호출만으로는 알림이 오지 않는다.

앱은 **CCCD write가 성공한 뒤에야** 연결됨으로 간주한다. 그 전까지는 연결 중이다.

### 배터리 잔량

표준 Battery Service(`0x180F`)의 Battery Level(`0x2A19`, 1바이트 %)을 쓴다.
자체 패킷 타입을 새로 만들지 않기로 했다 — 기존 패킷 규격을 건드리지 않아도 되고,
표준이라 앱 쪽 구현이 단순하다.

**선택 사항이다.** 기기가 이 서비스를 제공하지 않으면 앱은 잔량을 "알 수 없음(`--`)"으로
표시하고 나머지 기능은 그대로 동작한다. 유닛이 둘이므로 앱은 **둘 중 낮은 쪽**을 보여준다.

## 3. 체크섬

모든 패킷의 **마지막 바이트는 XOR 체크섬**이다.

```
XOR = 마지막 바이트를 제외한 전체 바이트를 순서대로 XOR
```

```c
uint8_t checksum(const uint8_t *p, size_t len) {  // len = 체크섬 제외 길이
    uint8_t x = 0;
    for (size_t i = 0; i < len; i++) x ^= p[i];
    return x;
}
```

수신 측은 **검증에 실패한 패킷을 조용히 버린다.** 일부 바이트만 반영하는 부분 갱신은
금지한다. 길이가 규격과 다른 패킷도 마찬가지로 버린다.

## 4. 수신 패킷 (기기 → 폰, notify)

### 4.1 거리 측정값 — 6바이트, 10Hz

```
[0xAA][d1][d2][d3][d4][XOR]
```

| 바이트 | 이름 | 설명 |
| --- | --- | --- |
| 0 | `0xAA` | 패킷 타입 (거리 측정값) |
| 1 | `d1` | CH1 거리 (cm) |
| 2 | `d2` | CH2 거리 (cm) |
| 3 | `d3` | CH3 거리 (cm) |
| 4 | `d4` | CH4 거리 (cm) |
| 5 | `XOR` | `0xAA ^ d1 ^ d2 ^ d3 ^ d4` |

- 전송 주기: **초당 10회 (100ms)**
- 거리 단위: **cm**, 부호 없는 1바이트
- **`0xFF` = 측정 실패 또는 미연결 센서.** 거리 255cm가 아니다. 유효 거리로 취급하거나
  최소값 계산에 넣으면 안 된다.
- 따라서 표현 가능한 유효 거리는 **0 ~ 254cm**다. 그보다 먼 거리는 254로 클램프한다.

패킷 자체는 자기가 앞인지 뒤인지 말하지 않는다. **어느 연결로 왔는지가 곧 방향이다.**

### 4.2 채널 ↔ 물리 배치

`d1`=CH1 … `d4`=CH4이며, **차량을 위에서 봤을 때 좌 → 우** 순서다. 앞뒤 유닛 모두 같은
규칙을 쓴다(운전자 기준 좌우). 앱의 부채꼴 4개도 같은 순서로 그린다.

> ⚠️ 실제 장착 시 좌우가 뒤집혔는지 반드시 실측으로 확인할 것. 뒤집혔다면
> **펌웨어에서** 바로잡고 앱은 건드리지 않는다.

## 5. 송신 패킷 (폰 → 기기, write)

앱은 두 유닛에 **같은 명령을 각각** 보낸다. 브로드캐스트 같은 건 없다.

### 5.1 거리 기준 변경 — 5바이트

```
[0xBB][near][mid][far][XOR]
```

| 바이트 | 이름 | 설명 |
| --- | --- | --- |
| 0 | `0xBB` | 패킷 타입 (거리 기준 변경) |
| 1 | `near` | 위험 기준 (cm) — 이 값 이내면 위험 |
| 2 | `mid` | 경고 기준 (cm) |
| 3 | `far` | 주의 기준 (cm) |
| 4 | `XOR` | `0xBB ^ near ^ mid ^ far` |

- 제약: `near < mid < far`, 각 값은 1 ~ 254. 어기면 기기가 패킷을 거부한다.
- 기본값: `near=30`, `mid=60`, `far=120` (주차 모드)
- 이 값은 **기기의 부저 경보 강도**를 정한다. 앱의 색 구간도 같은 값을 쓴다.
- 기기는 값을 비휘발성 메모리에 저장해 재부팅 후에도 유지한다.

앱에는 **주차 / 주행 두 모드**가 있고 모드마다 기준값을 따로 저장한다. 모드를 바꾸면
앱이 즉시 새 기준을 두 유닛에 밀어 넣는다. 주행 모드 기본값은 `20/35/50`으로 훨씬 좁다 —
주행 중에는 앞뒤 차가 1~2m에 있는 게 정상이라 주차용 기준으로는 부저가 쉬지 않고 울린다.

### 5.2 전원 제어 — 3바이트

```
[0xCC][mode][XOR]
```

| 바이트 | 이름 | 설명 |
| --- | --- | --- |
| 0 | `0xCC` | 패킷 타입 (전원 제어) |
| 1 | `mode` | `0x00` = 대기, `0x01` = 작동 |
| 2 | `XOR` | `0xCC ^ mode` |

- **대기(`0x00`)**: 센서 발사와 부저를 멈춘다. BLE 연결은 유지한다.
- **작동(`0x01`)**: 정상 측정/경보를 재개한다.
- 기기는 이 값도 비휘발성 메모리에 저장한다. 부팅 시 기본값은 **작동(`0x01`)** 이다.
  (원칙 1: 폰이 없어도 동작해야 하므로 기본이 꺼짐이면 안 된다.)
- 앱도 같은 이유로 **시작 시 한 번** `0x01`을 밀어 넣는다. 다만 자동 재연결 때는
  보내지 않는다 — 사용자가 방금 끈 것을 재연결이 되살리면 끄기 버튼이 무의미해진다.

## 6. 경보 강도 곡선

거리 기준 3개는 **경계선**일 뿐이고, 실제 경보는 그 사이에서도 연속적으로 세진다.
기기 부저와 앱이 **같은 곡선**을 쓴다.

| 거리 | 강도 |
| --- | --- |
| `far` 이상 | 0 (무음) |
| `mid` | 0.34 |
| `near` | 0.67 |
| 0cm | 1.0 |

구간 사이는 선형 보간이다. 강도 → 소리는 이렇게 매핑한다.

| | 울림 간격 | 음량 | 음높이 |
| --- | --- | --- | --- |
| 기기 부저 (액티브 부저) | 1000ms → 80ms (등비) | 고정 | 고정 |
| 앱 | 1000ms → 80ms (등비) | 35% → 100% | ×1.0 → ×1.45 |

강도 0.93을 넘으면 끊지 않고 연속음이 된다.

액티브 부저(HW-508)는 음색을 바꿀 수 없어 표현 수단이 울림 간격뿐이다. 앱은 음량·음높이도
같이 올린다.

구현: 펌웨어 `alarmIntensity()` / `beepIntervalMs()`,
앱 `android/.../protocol/AlarmCurve.kt`. **한쪽을 바꾸면 다른 쪽도 같은 PR에서 고친다.**

### 주행 모드는 이 곡선을 쓰지 않는다

주행 중에는 거리가 아니라 **접근 속도**로 판정한다
([ADR 0003](decisions/0003-app-alarm-and-drive-mode.md)). 앱이 최근 0.6초 동안의 접근
속도를 계산해 급접근일 때만 최대 강도로 울린다. 기기 부저는 위 곡선을 그대로 쓰되,
좁은 주행용 기준값(`20/35/50`) 덕분에 평소에는 조용하다.

## 7. 예시

거리 기준을 위험 25 / 경고 50 / 주의 100으로 바꾸는 패킷:

```
0xBB ^ 25 ^ 50 ^ 100
= 0xBB ^ 0x19 ^ 0x32 ^ 0x64
= 0xF4

→ BB 19 32 64 F4
```

CH1=45cm, CH2=120cm, CH3=측정실패, CH4=200cm인 측정값 패킷:

```
0xAA ^ 45 ^ 120 ^ 0xFF ^ 200
= 0xAA ^ 0x2D ^ 0x78 ^ 0xFF ^ 0xC8
= 0xC8

→ AA 2D 78 FF C8 C8
```

> 이 두 예시는 앱의 `ProtocolCodecTest`가 그대로 검증한다. 값을 바꾸면 테스트도 같이
> 고쳐야 한다 — 문서와 코드가 갈라지는 걸 막기 위한 장치다.

## 8. 타이밍과 연결 파라미터

- 측정값 패킷은 100ms 주기. 앱은 **1초 이상 패킷이 끊기면 "신호 없음"** 으로 본다
  (연결 자체가 끊긴 것과는 구분한다).
- 4채널을 순차 발사하므로 채널당 슬롯은 25ms다. 에코 타임아웃은 20ms(≈340cm)로 잡아
  슬롯 안에 들어오게 한다.
- MTU 협상은 필요 없다. 모든 패킷이 기본 ATT payload(20바이트) 안에 들어간다.
- 재연결은 지수 백오프(1s → 2s → 4s → … → 30s 상한, ±20% 지터). 유닛마다 독립이다.

## 9. 미확정 / 확인 필요

- [ ] **명령 ACK.** 현재 `0xBB` / `0xCC`에 대한 응답이 없다. 앱은 write 성공
      (`onCharacteristicWrite`)만으로 반영된 것으로 간주한다. 기기가 값을 거부했을 때
      앱이 알 방법이 없다.
- [ ] **현재 설정값 조회.** 앱을 새로 깔거나 다른 폰에서 붙었을 때 기기에 저장된
      거리 기준을 읽어올 방법이 없다. 그래서 **앱에 저장된 값을 진실로 보고**, 연결될
      때마다 기기에 다시 밀어 넣는다. 다른 폰에서 바꾼 값은 덮어써진다.
- [ ] **좌우 순서 실측.** 4.2절 참조. 앞뒤 유닛 각각 확인해야 한다.
